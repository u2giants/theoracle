# Synthetic documentary result custody

This implementation admits only already-existing synthetic documentary jobs. It does not authorize a private release, source ingestion, question generation, grading, provider dispatch, or production schema installation. Existing admission remains pending-only; result authority independently accepts pending or completed documentary views and denies other purposes. An absent result callback denies access.

Both fixed POST paths authenticate the five-field opaque envelope with the exact certificate URI and HMAC-SHA256 over `POST`, a newline, the exact fixed path, a newline, and the unchanged body bytes. No legacy body-only signature is accepted. The admission and result paths share a nonce namespace. A result nonce is committed with exclusive file creation, file synchronization and directory synchronization before result authority is resolved. Replays, malformed envelopes, drift, unavailable jobs and result failures receive a generic denial without enumeration.

The result callback requires a verify-full PostgreSQL connection with a pinned CA and verifies actual libpq TLS on each connection. External settings and custody retain the independently pinned release/runtime policy. SQL009 grants only one fixed SECURITY DEFINER function to the gateway metadata group; it grants no private original, receipt, query or pack table SELECT. Its projection returns only current legitimate status and canonical receipt bytes.

Before any result bytes become available, the transaction holds authorization and selector advisory locks, fixed synthetic ledger table SHARE locks, and job/receipt row locks. These prevent source catalog, receipt, appointment, artifact invalidation, watermark and selector phantoms or changes through delivery. They temporarily block other writers in the dedicated synthetic namespace; no legacy or shared POP database is authorized. Lock waiting is bounded to two seconds and statements to five seconds. Deadlock/lock timeout fails closed; a fresh nonce may retry this read without a provider request.

The current job's actor, source appointments and parent lineage, expiry, source revision/status, confirmed draft, native original/reading/parser receipts, artifact state/dependencies, selector/watermark, release/runtime/admission seals and immutable pack receipt are rechecked before the first byte. Pending jobs return only the fixed pending state with HTTP202. Completed jobs return HTTP200 with byte-exact stored canonical receipt bytes, including original numerical and Unicode spelling; receipt hash and JSON equivalence to the job pack are verified. Stored bytes must remain within the sealed query limit, and the absolute response limit is 131,072 bytes.

The callback context remains open across one socket send-all operation. Its absolute five-second deadline starts before entering result custody; the remaining deadline determines the socket timeout. Current expiry and the unchanged external policy are checked immediately before writing. Authority locks are released when delivery finishes or fails. A bounded lease cannot retract bytes already sent, and later revocation affects subsequent requests; this is not an instantaneous unsend guarantee.

Focused tests use invented records in a freshly created/dropped local database with actual SCRAM authentication and verify-full PostgreSQL TLS. They cover strict mTLS sockets, byte-exact completed delivery, opaque pending delivery, malformed/tampered/expired requests, cross-purpose signatures, shared nonce replays, revoked sources/appointments, receipt tampering, oversized results, default private denial and in-flight revocation blocking. The reused owner fixture supports TLS/SCRAM but also permits a deliberately plaintext client; server-side plaintext rejection is not claimed. Hosted runtime clients require verify-full, while the separately owned new bootstrap fixture must enforce its stronger server policy.
