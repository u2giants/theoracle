### Disagreements and corrections (including where I contradict your independent position)

**D1 — "Exact filter bytes cannot be exported with current privileges" is an unverified factual premise, and the wrong wording for a plan.** `PTRACE_SECCOMP_GET_FILTER` exists precisely to return a tracee's installed filter program, and your own design already parks the child in a ptrace-visible stop state (step 9) with a same-UID parent. Whether self-export or parent-ptrace export succeeds on the target kernel is a qualification fact, not a design fact. Confidence: moderate (I did not and will not test it). Minimum clarification: restate as *"we do not rely on exported filter bytes"*, and add a qualification step that attempts export against the pinned digest and records either a match or a documented refusal. If export works, the evidence model strengthens; it must never become a precondition that lets a weaker install pass.

**D2 — The self-stop's safety argument is checked in the wrong order.** v2 justifies `kill(0, SIGSTOP)` by "independently checked new session", but the ordered bootstrap only rechecks FDs/limits/maps/NNP/Seccomp at step (10) — i.e. *after* the child has already issued the group-scoped stop. If `setsid` isolation is not what the parent believes, `kill(0,…)` targets the parent's group, not the child's, before any check can refuse. Confidence high. Minimum clarification: (a) child asserts `getpgrp()==getsid(0)==getpid()` pre-seal, immediately before NNP/seccomp, as part of the fixed bootstrap; (b) parent reads `/proc/<pid>/stat` pgrp/session fields and matches the `Popen` pid *before* treating a stop as the handshake; (c) parent terminates with `killpg`, never pid-only kill (see D6). No weakening: `setpgid`/`setsid` remain default-denied post-seal, so the assertion is stable.

**D3 — The self-stop cannot be made one-shot, and the parent must survive a late stop.** `kill(0,SIGSTOP)` stays allowed for the process lifetime; seccomp cannot restrict it to "once". v2 says a second stop is killed, but does not say the *final* wait tolerates a stop. If the child stops after a complete frame and before `exit_group`, a blocking wait hangs to the deadline. Minimum clarification: the parent's terminal wait is a `WNOHANG|WUNTRACED` loop against the original monotonic remaining, a stop after handshake is a refusal (kill group, reap), and a complete frame plus stop is never success.

**D4 — Normal interpreter shutdown is a guaranteed SIGSYS path, and `close` is not the only reason.** Your point 1 is correct but understates it: `Py_Finalize` closes `sys.stdout`/`sys.stderr` and any `os.fdopen` wrapper (close is not in the allowlist), and atexit handlers registered during preload would run. `_read_private_archive_v1` also cannot be entered via `os.fdopen(os.dup(...))` as `_verify_replacement_archive_fd_v1` does (`forward_recovery.py:259`) because that wrapper seeks (`:260`, `:263`) on a non-3/4/5 fd and the whole verifier uses `fcntl` (`:256`) and `fstat` (`:257`, `:266`) that are denied or fd-restricted post-seal. Minimum clarification: the child entrypoint is an explicit *write-all bytes frame → flush → `os._exit(0)`* path (no `sys.exit`, no return through `main`, no atexit), and the parent treats any `SIGSYS`/nonzero status, including one after a complete frame, as refusal. Confidence high.

**D5 — The sole result record contradicts "parent rusage from actual wait4, never child claims."** `RecoveryArchiveChildResultV1` *requires child-authored* `actual_memory_limit_bytes`, `actual_max_rss_kib`, `actual_user_seconds`, `actual_system_seconds` (`recovery_contracts_v1.py:961-964`), with float-typed coercion checks (`:974-978`). A child cannot `wait4` itself, and `getrusage` is not on the allowlist. This is the largest unresolved ownership contradiction in v2. Minimum clarification: state which fields are child-authored observations and which are parent-filled after `wait4`; if rusage moves to the parent, that is an incompatible observation and belongs in the explicit protocol-v2 record the plan already reserves — not in the v1 record with optional fields. Also `_verify_replacement_archive_fd_v1` reports `total_bytes: inventory.total_bytes` (`:268`), i.e. a DTO value, not the observed total accumulated at `:202`; the plan's "observed result" must derive totals from the policy, and the parent must recompute rather than trust either source.

**D6 — "Actual wait4" has no owner in the current execution body, and its timeout path is wrong for this design.** `_run_bounded_docker_v1` is `subprocess.run(...)` (`forward_recovery.py:49-54`), which pops `waitpid`, exposes no per-child rusage (`resource.getrusage(RUSAGE_CHILDREN)` is cumulative), and on timeout kills **the pid**, not the group, then reaps via the same machinery. For the child branch the parent needs `os.wait4` (or an equivalent fixed waiter), an exclusive reaper (Popen must not also wait), `killpg` for watchdog and refusal paths, and deadlock-free pre-exec limits — `preexec_fn` in a multithreaded parent is a documented hang hazard (`:52` already uses it). v2's "single-threaded bootstrap" is about the *child*; it must not be read as licensing `preexec_fn` in a threaded server. Confidence high. Minimum clarification: name the concrete waiter, the group-kill path, and the pre-exec limit mechanism (or a fixed single-threaded launcher), and state that the old `BoundedDocker` timeout enum (`:30`) is not reused as deadline authority.

**D7 — Allocator feasibility: "deny brk" requires more tunables than v2 names, and v2 contradicts itself on how tunables enter.** With a single arena and `mmap_threshold=0`, glibc's main arena still grows by `sbrk` before seal and, after seal, `_int_free` on the main arena calls `systrim` → `MORECORE` → **brk** when a freed chunk is ≥ `mp_.trim_threshold` (default 128 KiB); `malloc_trim`/`madvise` paths are sibling hazards. Parsing a multi-thousand-entry inventory (max 4096 files, `restore_receipts.py:277`) and pydantic object graphs will produce ≥128 KiB frees. So `M_TRIM_THRESHOLD`/`M_TOP_PAD` must be pinned alongside `M_ARENA_MAX`/`M_MMAP_THRESHOLD`, or a legitimate success path dies on SIGSYS. Confidence moderate-high (mechanism is standard glibc; no experiment performed). Second, v2 says both "no … glibc tuning variables can enter outside the installed variant" *and* "fixed documented glibc tunables" — these are only compatible if the installed allowlisted environment contains an exact pinned `GLIBC_TUNABLES` value (a security-sensitive, boot-strap-time channel) or the child calls `mallopt` pre-seal through a preloaded handle. Pick one and name it. Third, mmap-per-allocation is bounded by `vm.max_map_count`, not `RLIMIT_AS`; v2 correctly separates AS/RSS/heap/filesystem but omits VMA count, which is the real ceiling here and is not in the installed resource authority read at `recovery_authority_v1.py:381-382`. Add it (reading it is a parent-side read; refusal on headroom is the right outcome, not allowlisting brk).

**D8 — seccomp without `TSYNC` does not match "thread count 1".** The plan verifies thread count at step (7) and installs the filter at step (8). A filter without `SECCOMP_FILTER_FLAG_TSYNC` binds only the installing thread; a pre-existing second thread escapes entirely. Minimum clarification: install with TSYNC and refuse if TSYNC reports a failing tid; re-read thread count post-install and again at the stop. Confidence high.

**D9 — `-I -S -B` with no `PYTHON*` environment makes pydantic/pydantic_core unimportable.** `-S` suppresses `site`, so site-packages is not on `sys.path`; `-I` suppresses the script directory and user site; `PYTHONPATH` is forbidden by v2. Yet the child must use the existing record owners (pydantic; `recovery_contracts_v1.py:915-983`, `restore_receipts.py:274`) whose native core is a mapped extension. Minimum clarification: the fixed entrypoint inserts an exact, installed-metadata-derived, closed absolute `sys.path` list pre-seal (no `.pth` processing, no caller-selected path), and that extension's backing file is inside the required executable-mapping closure. Without this the variant is unsupported by construction, not by experiment.

**D10 — The manifest FD and "full closure" verification are parent-scoped and grossly mis-sized for the child.** `_observe_installed_runtime_census_v1` depends on the parent `ContextVar` deadline (`recovery_authority_v1.py:369-370`, `380`) and permits a 32 GiB aggregate census (`recovery_contracts_v1.py:990`); the memory "authority" it reads is `SC_AVPHYS_PAGES` availability (`recovery_authority_v1.py:381-382`), which is not a per-process ceiling. If step (6) is read as "child hashes the whole installed census pre-seal," the original window is gone before any archive byte. Minimum clarification: child step (6) is scoped to *actually loaded executable mappings and their named backing files* (plus the control's declared seals) inside the remaining window; whole-census verification stays with the parent, and the hard `RLIMIT_AS` value must be named explicitly as `min(installed allowance, …)` with its provenance, not inferred from free-page availability.

**D11 — stdin/close ordering inside step (8) is stated twice, differently.** The prose says fd 0 is closed "BEFORE seal"; step (8) bundles "close stdin, install NNP and pinned seccomp". In a closed-syscall design the exact byte ordering matters (`close(0)` must precede the filter's activation). Make it atomic in the text: close 0 → NNP → seccomp(TSYNC) → verify → self-stop.

**D12 — Minor but real: "existing filters … may only restrict further" is unexercisable.** `prctl`/`seccomp` are denied post-install, so no second install path can exist. Keep the invariant, delete the implication that a further-restriction path is available, and say explicitly that the source contains exactly one install site.

Also noted, not as objections: CPython's startup `fstat(0/1/2)` and `isatty` (ioctl/TCGETS) are pre-seal, so the fd-1/2-restricted `fstat` allowlist is consistent *only if* no wrapper is constructed post-seal — v2 says this, keep it. `munmap` is argument-unconstrainable in BPF; that is acceptable only because no untrusted code executes post-seal and `mprotect`/`exec` mappings are denied — say that rather than implying munmap is "narrowly constrained". The existing streaming path is at least test-touched through `tests/test_recovery_streaming_archive_v1.py:16-45`, with a `<1 MiB` peak regression (`:25`) that supports the "no A-sized warmup" claim; a multi-member, >1 MiB same-policy regression belongs in the source packet. And vdso byte equality is not generally stable across boots/CPU alternative patching, so "independent installed kernel-base byte commitment" must be pinned per actual boot/CPU variant at qualification, not at package-install time — otherwise D-vdso turns into a permanent refusal. Confidence moderate.
