# Review of the Oracle consultant plan (#24) and its implementation — October 27, 2026

Written for Albert. Plain findings, then recommendations. Evidence references are for the next AI session, not for Albert to open.

## Short answers

**a) Is the plan the right plan?** No. The goal statement (section 1) is excellent and matches what you want. The 16-step sequence underneath it does not. "Seeing the big picture across many small documents" is scheduled as step 9 of 16 (S09), after interviews, meetings and in-meeting participation. There is no step at all for holistic synthesis (a layer that reads across all documents and writes a company-level picture). The first "usable journey" (S03) is defined as one document in, one cited answer out. That is the same shape as the old system that failed.

**b) Has the AI implemented it well?** It has been careful and busy, but mostly with itself. In 30 days and 172 merged pull requests: 2 of 16 steps are checked, both accepted on synthetic data only. Roughly 40% of pull requests are documentation, status, handoff or "preserve/record" changes; most of the rest are fixes to infrastructure plumbing (TLS, workers, flaky tests). The last real contact with company data was October 11, when the system was found to be "a keyword matcher and quotation assembler" and ingestion of your documents failed. Nothing real has been attempted since.

**c) Errors in plan and code.**
1. The default answer engine today is still a keyword matcher with no AI model in it (graph/evidence_answer.py). The one real AI extraction pipeline (graph/graphrag.py) is locked behind a "preview" switch, has never been run against a model in any test, and works by pasting every document into one prompt, which cannot scale to many documents.
2. Promised components are not actually used: Graphiti is installed but never imported; Docling is installed but never called; the "global summary" module labels coverage and summarises nothing; there is no vector/semantic search at all; recommendations are data shapes with generation hard-coded to "paused".
3. The codebase is ~52,000 lines of product code plus ~60,000 lines of tests. About a third of the product code is security, custody, TLS and permission scaffolding; the interview module is 228 lines and the consultant module 93. There are 2,313 "permission denied" statements, one every 22 lines. Half the tests check that something is refused.
4. The plan documents have become unreadable: 16 plan files totalling 1.6 MB, a 210 KB main plan whose status block alone is 450 lines of hashes and run IDs, and 42 handoff files. Letter schemes S, H, W, U, R, Q overlap.
5. The plan's own stop rule (section 13: stop broadening scope if S03 cannot show connected understanding; failure is not a reason to add more agents or another database) has been violated continuously since October 11. Work on backup/recovery (S13) and product polish (S12) proceeded while S03 stayed unaccepted.
6. The real-user test (#58) was deferred until all 16 steps finish. That inverts the plan's own "thin usable journey first" principle.
7. The stack (FalkorDB + Graphiti + Docling + LangGraph + pm4py + Trigger.dev Python + Next.js + Supabase + mutual TLS + hand-rolled seccomp) is disproportionate for one company and a few dozen documents. Most fix PRs are integration failures between these parts.
8. The evidence-first design made rigor an input gate: nothing is indexed until it is "qualified". A consultant that will not read messy documents cannot see a picture made of messy documents. Rigor belongs in the output (label what is policy, practice, report, inference), not as a barrier to reading.

**d) Improvements.**
1. Freeze the 16-step plan. Replace it with one short plan with a single deliverable: take the ~30 real documents you already have, run them through an AI model end to end (read every document → extract people, processes, steps, hand-offs, rules, exceptions → merge and deduplicate across documents → write a company-level synthesis of how work flows), and put that synthesis in front of Ilona. Her reaction, not a test count, decides what to build next.
2. Build the big-picture layer first, not ninth. Concretely: (i) a per-document structured read; (ii) a cross-document merge step that resolves the same person/process/system named differently; (iii) hierarchical summaries (department → company) in the style of GraphRAG "community summaries", which is exactly what codos.ai's "company-merge-judge" and three-vault memory do. This is the mechanism that lets small fragments add up to a picture.
3. Use a real model in the loop every day. Every test of the answer path must call an actual model on real (or realistically messy) documents. Deterministic-only tests cannot prove understanding.
4. Keep evidence as labels and links, not as gates. Every statement in the synthesis cites its sources and is tagged policy / observed / reported / inferred. Nothing waits for approval before it can be read; approval only upgrades a statement to "confirmed".
5. Cut the stack to what is needed now: one database (Postgres with pgvector), one AI provider, one worker. Reintroduce a graph database only if a measured question cannot be answered without it.
6. Governance diet: one plan file under 5 pages with a 20-line status; retire all other Oracle plan files and the handoff pile into an archive folder; no SHA256 receipts or run IDs in status text; one reviewer gate only for production and database structure, none for prototypes.
7. Reinstate the real-user test immediately as the acceptance criterion for every milestone, with you and Ilona as the judges, on your real documents.

## Design direction after Albert's eight points — October 27, 2026, evening

**1. Scale: hundreds of documents, diagrams, tens of thousands of transcript lines, plus live interviews.** This rules out the current Oracle 2 answer path, which pastes every document into one prompt. It also rules out "read everything at question time". The system must read once, structure once, and keep a maintained company map that questions are answered from. The map is rebuilt incrementally as sources arrive.

**2. No thin journey, no atomic-claim grading.** Agreed, and the earlier recommendation is withdrawn. The first deliverable is the whole corpus ingested and a company-level map produced: departments, roles, processes, hand-offs, systems, recurring pain points, with each item linked to the sources behind it. Nobody grades individual claims. People react to the map.

**3. ScaleDown.** Yes, for a large share of the volume. Report saved at `scaledown-report.md`. What ScaleDown can take: classifying every passage and transcript turn by type (process, responsibility, rule, reference, complaint, decision); pulling flat facts out of each passage (people, roles, systems, steps, artifacts, metrics, dates, quotes); labeling things (policy vs. practice vs. complaint, department, contradiction yes/no); compressing retrieved context before a frontier call; per-chunk summaries once summarization leaves private preview. By call count that is roughly 70–80% of all model calls. What must stay with a frontier model: inferring relationships between facts (what hands off to what, what depends on what, what is an exception), merging the same entity under different names across documents, writing the community/department/company summaries, answering questions, generating recommendations, and running interviews. Diagrams and flowcharts need a vision model; ScaleDown has none.

**4. No complicated permissions.** Agreed. Keep ordinary login and an admin role. Delete the candidate/confirmed credential split, the TLS and custody layers, the authority-grant chain, the seccomp sandbox, and the 2,300 refusal checks. That is roughly a third of the current product code and most of the test suite.

**5. FalkorDB stays.** The earlier "reintroduce only if needed" line was a reaction to integration churn, not a judgment on the database. A graph is the right home for the big picture, and ripping it out later would be the reprogramming Albert wants to avoid. Keep FalkorDB as the one graph store from day one. Keep Postgres for the raw sources, extracted text, embeddings (pgvector) and the audit trail, with the graph rebuildable from Postgres so a bad extraction run can be redone without losing sources.

**6. Why the old system could not connect disparate documents, and what is different.** The old system stored isolated text chunks with vectors and looked up a few nearest chunks per question. Nothing ever joined "Jessica" in a licensing PDF to "J." in a transcript, or placed both inside one process. The new mechanism has four parts, all of which must exist for cross-document connection to work:
- Entity resolution: every extracted person, role, system, process or artifact is merged into one canonical node, using exact name match, alias tables, embedding similarity, and a frontier-model judge for the ambiguous cases. This is the single most important piece and the one the old system lacked.
- Typed edges across sources: each relationship (performs, hands off to, depends on, uses, is an exception to, contradicts) is an edge in FalkorDB that carries its source references, so an edge discovered in document A and one in transcript B meet at the shared node.
- Community detection and hierarchical summaries: run a graph clustering (Leiden) to find clusters of connected nodes, then have a frontier model write a summary of each cluster, then summaries of summaries up to the company level. This is the Microsoft GraphRAG pattern and is what makes "what are our biggest cross-department bottlenecks?" answerable; local vector search cannot answer it.
- Two query modes: local (walk the graph around the entities named in the question) and global (map over community summaries and reduce). The old system had only the local mode, without a graph.
Honesty: no design is "sure" until it is run on the real corpus. The plan therefore includes a standing evaluation: twenty questions whose answers require combining at least three sources, written once by Albert and Ilona, rerun automatically after every ingestion change.

**7. Implementable by GLM 5.1 or Sol 6.1.** The plan must be written as numbered steps, each with exact table definitions, exact JSON shapes for every model call, exact prompts, exact acceptance tests with fixture files, and no step larger than a day. No step may require inventing a design. That document does not exist yet; writing it is the next job.

**8. Human time within reason.** Three touchpoints only: (a) Albert and Ilona write the twenty evaluation questions once, about an hour; (b) at each milestone they read a one-page company map and mark what is wrong, about thirty minutes; (c) the system keeps a short list of its own unresolved questions ("is this the same approval as that one?") and asks the relevant employee in Teams, one or two questions at a time, with a weekly cap. Interviews are ten minutes, asynchronous, and the employee can stop at any point. No per-claim approval queue.
